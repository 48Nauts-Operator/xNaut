# XNAUT-199 report: terminal triggers, one path

## The decision

**Kept the frontend path. Deleted the Rust one.**

What I read before deciding:

- `src/js/app.js:6075` (old numbering) `checkTriggers`, called at `app.js:2899`
  from the `terminal-output:<id>` listener. localStorage-backed, keyword and
  regex, one action: `showNotification`.
- `src-tauri/src/triggers.rs` `process_output`: `#[allow(dead_code)]`, no
  caller anywhere in the crate. It emitted `trigger-notification`,
  `trigger-command` and `trigger-ai-assist`; a grep across `src/js` finds no
  listener for any of the three.
- `src-tauri/src/commands.rs:130-186`: `create_trigger`, `list_triggers`,
  `delete_trigger`, `toggle_trigger`, all registered in `main.rs:199-202`. Only
  `create_trigger` was ever invoked from JS. Nothing called `list_triggers`, so
  the backend store was **write-only**: a delete or a toggle in the UI never
  reached it, and `AppState.triggers` is an in-memory `HashMap` that is never
  persisted, so it emptied on every restart anyway.

Why the frontend won:

1. It is the path the UI actually describes. The edit modal collects a name, a
   pattern type, a pattern, a **notification message** and an enabled flag.
   Nothing else.
2. Choosing Rust was not "wire up one call". To deliver anything a user could
   see it needed persistence, full CRUD sync from the frontend, keyword support
   (Rust had regex only), three new frontend listeners, and new UI for the
   command and prompt fields. That is a feature build, next to the flush loop
   that caused the freeze in #54.
3. The one thing Rust bought that the frontend lacked was coverage of PTY
   sessions with no xterm. That cost two lines to recover in JS (below), not a
   backend.

## The brief was wrong about one thing

> The trigger UI offers three actions and delivers one.

It does not. `src/index.html:572-610` is the whole trigger editor and it has no
action selector, no command field and no prompt field. The only action the UI
has ever offered is a notification, and the frontend delivers it. The three
actions existed in `TriggerAction` and in the dead `triggers.rs`, never in the
UI. So "the UI must stop offering the ones that do not work" had nothing to
remove; the honest fix was to delete the backend that promised them.

## What changed

**Deleted (the second path)**

- `src-tauri/src/triggers.rs` and `mod triggers;`.
- The four trigger commands in `commands.rs` and their registrations in
  `main.rs`, plus `test_trigger_action_serialize`.
- `Trigger` / `TriggerAction` and the `AppState.triggers` field in `state.rs`.
- `XnautError::TriggerNotFound` / `InvalidTriggerPattern` in `errors.rs`, both
  unreferenced.
- The four ACL permissions in `src-tauri/permissions/default.toml` and their
  entries in the default set. `gen/schemas/*` regenerated by the build.
- `invoke('create_trigger', ...)` in `saveTrigger`, the write-only call.
- The `#triggers-settings-list` div in the Triggers settings section. Nothing
  ever wrote into it, and `.settings-group` gives it a border and 20px of
  padding, so it rendered as a permanently empty box.

**Fixed in the surviving path**

- `checkTriggers` was matching the raw PTY chunk. That chunk carries its escape
  sequences, and OSC 7 puts the working directory in it, so `cd ~/error-logs`
  fired an `error` keyword trigger on the path rather than on any output. It now
  strips OSC and CSI sequences before matching, which also fixes the other
  direction: a word a colour code ran through (`\x1b[31mfai\x1b[0mled`) was
  never matched before.
- A trailing comma in a keyword pattern (`error,`) produced an empty keyword,
  and every string contains `''`, so the trigger fired on all output. Empty
  keywords are dropped.
- Added a 10 s per-trigger cooldown. Output arrives one flush per 16 ms; a
  streaming agent that printed "error" once notified on every chunk that still
  held the word. This was required by the next change, not optional polish.
- Agent Space renders its own panes and never creates an xterm, so its PTY
  output reached no trigger at all. `app.js` now exposes
  `window.xnautCheckTriggers` (same pattern as the existing
  `window.xnautNotify`) and `agent-space.js:1139` feeds it the same decoded
  chunk it gives the parser.
- The cooldown also collapses the one duplicate the Agent Space hook could
  create: a session watched by both an open terminal pane and a live Agent
  Space turn now notifies once, not twice.
- The Triggers settings blurb said "trigger actions automatically". It now says
  what it does: match a keyword or a regex and raise a desktop notification.

## What I proved

`scripts/triggers-smoke.cjs` lifts the shipped `checkTriggers` out of `app.js`
with a regex and runs it, so it tests the real function and not a copy that can
drift. It covers: keyword match and non-match, regex match, an invalid regex not
killing the triggers after it, disabled triggers, the OSC 7 false positive, the
colour-split word, the trailing-comma empty keyword, 60 consecutive flushes
producing one notification, and the cooldown expiring. It then asserts both
feeds still call it, and that the deleted backend path has not grown back
(`triggers.rs` absent; no `create_trigger` in `main.rs`, `commands.rs` or the
ACL; no `Trigger` types in `state.rs`; no `invoke('create_trigger'` in
`app.js`), plus that none of the three events is emitted again without a
listener.

Five entries added to `scripts/mutation-check.cjs`. Each was run: break the
code, confirm the check goes red, restore.

## What I did not do

- **No live app run.** There is a running xNAUT I was told not to touch, and a
  dev build in this worktree would restart it. The trigger logic is proved at
  the layer under the desktop notification: `showNotification` is injected in
  the smoke test, so everything up to the OS call is exercised. The OS
  notification itself (`new Notification(...)`, `app.js`) is unchanged.
- **No coverage for PTY sessions nobody is watching.** Frontend triggers fire
  while a listener exists: a terminal pane with an xterm, or an Agent Space turn
  in flight. An agent launched into a background tab whose terminal has not been
  created yet still misses triggers until it is opened. Closing that gap is what
  the backend path would have bought, and it needs the whole backend build
  described above; it is not something to leave half-wired again.
- **Did not touch the `.settings-group` styling or the 58 pre-existing lint errors.**
