# Open-Dots compared with xNaut: personal Nauts and a mobile client

Reviewed 2026-09-30. Open-Dots source: `617ac65fca19a524e9747b69b08ff398a60516b2`. xNaut source: `04a7f2d526821b1ff37948a4cf8021349f34a822`, in `.worktrees/action-execution-evidence`. This is a source review, not an installed-product or live-runtime test. No Open-Dots dependencies, application code, containers, or tests were executed. The repository was cloned read-only for inspection outside the product repositories. A Python standard-library symbol-table check parsed its chat source without importing it.

## Answer

**Yes: xNaut can provide the tools, identity, execution, and supervision backend for Open-Dots-style personal Nauts, with a mobile app as the interface.** Much of the foundation already exists, including a phone companion bridge. The main work is packaging the existing internals behind a stable, appropriately scoped mobile API and making conversation/run synchronization reliable. A fresh agent engine or a fork of Open-Dots is not necessary.

The phone would create/select a Naut, send a request, see evidence and artifacts, and answer approvals. The host running xNaut and its configured workers would perform the work. A phone client does not make desktop/VM execution available when its host is offline.

This finding concerns the inspected xNaut development revision. In particular, `create_worktree` and `start_repository_task` are **preview work, not features to claim in public release 1.28.2**. Other statements below establish source presence, not a release certification.

## What Open-Dots actually implements

Open-Dots has a Next.js/React client and Python/FastAPI server. Bots are personas with prompts, model selections and appearance; its backend stores messages, bot records, settings, approvals and audit events in local SQLite. Credentials use a Fernet secret store. It is a single-owner application; schema tables named `users`, `tasks`, and `memories` are not evidence of implemented multi-user access, durable job scheduling, or semantic memory. [README](https://github.com/Anil-matcha/open-dots/blob/617ac65fca19a524e9747b69b08ff398a60516b2/README.md), [database implementation](https://github.com/Anil-matcha/open-dots/blob/617ac65fca19a524e9747b69b08ff398a60516b2/server/app/services/database.py)

Its model adapter submits a custom prediction request to `base_url/model_id` using `x-api-key`; it optionally polls prediction results. It formats the latest ten previous messages into the system prompt and emits the completed answer as small SSE text chunks. This is not a generic OpenAI-compatible tool-calling integration or necessarily upstream token streaming. Model catalog entries alone do not establish provider compatibility. [Provider source](https://github.com/Anil-matcha/open-dots/blob/617ac65fca19a524e9747b69b08ff398a60516b2/server/app/services/provider_service.py)

The important distinction is **explicit actions versus autonomous agents**: the chat route parses workspace/connector slash commands from the last user message, executes one governed action, then supplies its result as context to a text model call. Computer controls are separate API/UI operations. I found no model-returned tool-call parsing or observe/plan/act loop in this path, and no repository-worktree orchestration, worker delegation, or test/merge/release workflow. [Chat route](https://github.com/Anil-matcha/open-dots/blob/617ac65fca19a524e9747b69b08ff398a60516b2/server/app/routers/chat.py), [computer router](https://github.com/Anil-matcha/open-dots/blob/617ac65fca19a524e9747b69b08ff398a60516b2/server/app/routers/computers.py)

The action gateway is nevertheless useful design: an explicit registry rejects unknown actions, records structured intent/target/arguments/risk, gates actions through approvals, and emits redacted lifecycle audit events. Registered workspace reads as well as writes request approval by default; computer lifecycle/status operations have different approval settings. Composio provides OAuth plus narrowly implemented GitHub issue lookup/create actions, not arbitrary connector tool discovery. Approval records persist, but waiting futures and gateway pending invocations live in process memory, so database persistence is not restart-safe job continuation. [Gateway](https://github.com/Anil-matcha/open-dots/blob/617ac65fca19a524e9747b69b08ff398a60516b2/server/app/services/action_gateway.py), [approval broker](https://github.com/Anil-matcha/open-dots/blob/617ac65fca19a524e9747b69b08ff398a60516b2/server/app/services/approval_broker.py), [connector actions](https://github.com/Anil-matcha/open-dots/blob/617ac65fca19a524e9747b69b08ff398a60516b2/server/app/services/connector_actions.py)

The optional Docker provider is real implementation, alongside a fake default provider and remote adapter. Each bot gets a container workspace and Playwright browser, with navigation, screenshots, click/type/keypress/scroll, shell commands and file listing. Containers run as `pwuser`, have read-only roots, dropped capabilities, limits and loopback-published runtime ports. The driver operates Chromium pages; it is not general macOS/Windows desktop automation. The project itself disclaims hardened isolation for hostile websites. [Docker provider](https://github.com/Anil-matcha/open-dots/blob/617ac65fca19a524e9747b69b08ff398a60516b2/server/app/services/docker_computer_provider.py), [browser driver](https://github.com/Anil-matcha/open-dots/blob/617ac65fca19a524e9747b69b08ff398a60516b2/runtime/driver.mjs)

There are focused Python tests for gateway policy, auth, persistence, workspace confinement, connectors and fake/mocked Docker/remote providers. Their presence does not establish a live model-to-browser scenario. I did not run them. [Test sources](https://github.com/Anil-matcha/open-dots/tree/617ac65fca19a524e9747b69b08ff398a60516b2/server/tests)

**Concrete defect found by static inspection:** `event_generator()` assigns `system_prompt` at chat.py line 205, which makes it a local variable throughout that nested function, yet it reads it before assignment both there and at line 212. A standard-library `symtable` inspection confirms `local=True, free=False`. Normal chat should therefore encounter `UnboundLocalError` when reaching inference, absent a fix. The route also maps provider completion to `ok: True` without preserving a false provider result. These are source findings, not observations from launching the app. They reinforce treating this revision as a prototype rather than a verified ready-made backend.

## xNaut comparison from source

| Area | Open-Dots | xNaut inspected revision |
|---|---|---|
| Agent identity | Persona prompt/model/avatar | Persistent profile with role, capabilities, execution target and independently selected chat/runtime model/provider |
| Model/work execution | Custom prediction API and explicit actions | Real chat tool loop with native/MCP tools, plus coding CLI workers including Codex and Claude |
| Coding isolation | Confined workspace operations; optional container workspace | Git worktrees plus selectable local/exe.dev/GitVM execution; worktree isolation alone is not an OS sandbox |
| Orchestration | No worker/task orchestration found in reviewed paths | Ticket dispatch, swarms, verification records, merge risk gate, release state machine |
| Computer UI | Optional bot-scoped Playwright browser controls and screenshot view | Embedded browser panes exist, but these are not equivalent to a bot-scoped autonomous screenshot/action service; external runtime/MCP capabilities depend on configuration |
| Durable state | SQLite conversations/settings/audit; pending actions also in memory | Profile/config stores, SQLite conversation revisions, ticket/run evidence, durable terminal sessions; not one unified remote job API |
| Permissions | Small explicit deny-by-default action registry | Agent capability filtering, runtime launch policies, tool hooks, approval/inbox gates; enforcement differs by runtime, and network policy is explicitly advisory in the policy metadata |
| Mobile | No dedicated mobile client in inspected repo | Existing phone PWA, authenticated REST bridge, WebSocket terminal mirror, device registration/revocation, inbox and artifacts |

xNaut evidence: `src-tauri/src/agent_profiles.rs` (profile schema and Tauri commands), `agent_tools.rs` (multi-round tool loop, native tools, MCP and tool-catalog integration), `agent_work.rs` (preview self-service worktree/launch tools), `dispatch.rs`, `swarm.rs`, `sandbox_verify.rs`, `policy.rs`, `browser.rs`, and `conversation_store.rs`. These are in the inspected worktree, not inferred from README slogans. Policy source explicitly distinguishes enforced/advisory controls and notes a broken veto script can fail open; do not represent all xNaut permissions as a uniform hard sandbox.

The preview launch tools already use an authorized repository list, stable per-agent/task workspace keys, an exclusive on-disk reservation and launch receipts. They distinguish workspace preparation, launch and completed verification. A mobile API should preserve those distinctions, including the current crash-reconciliation limitation on pending reservations, rather than treating every successful request as completed work.

## Existing mobile foundation and actual gaps

`src-tauri/src/mobile.rs:161` starts an Axum server, normally on port 8931. Its routes include session creation/listing/files/git, artifact browsing, observatory status, interruption/stop, agent wake, automation listing/run, inbox decisions/answers, device registration/revocation and vault search. `/ws/:session_id` mirrors PTY interaction. The static phone UI is `src/mobile.html`. `main.rs:933` starts the bridge inside the desktop app.

Authentication already includes random pairing tokens, constant-time checking, per-device revocable tokens and Bearer-header support. However, the bridge binds `0.0.0.0`, uses HTTP and assumes Tailscale/WireGuard transport protection. Binding does not itself restrict traffic to the tailnet. All accepted device tokens currently confer broad owner access, including terminal input, device management and `/api/control/eval`, which evaluates JavaScript in the app webview. This is a trusted-owner companion design, not an internet-facing or multi-user product boundary.

The router does **not** expose typed APIs for Naut profile CRUD, conversational turns/history, or durable run event replay. Those underlying capabilities largely exist as Tauri commands (`agent_profile_create/update`, `agent_chat_turn`, conversation storage), so wrapping shared service logic is credible. Driving `/api/control/eval` from a mobile app would be a brittle and overprivileged substitute.

The bridge depends on `AppHandle` and app state. Some Zellij-backed worker sessions survive app exit, but the bridge does not become an always-on independent service. A phone-only experience eventually needs a managed persistent host or a separate headless service. `push.rs` implements optional ntfy delivery; per-device APNs tokens are recorded, but native APNs sending is preparatory, not implemented there.

## Realistic first version

```text
Mobile PWA / native client
    -> paired, authenticated private connection
    -> xNaut typed Naut/conversation/run/approval API
    -> existing identity + chat tools + authorized execution services
    -> local runtime / exe.dev / GitVM
    <- durable run events, approval requests, artifacts, verification evidence
```

1. Start with a single owner's mobile Naut list, profile setup, chat and task submission; reuse xNaut profiles and conversation storage as the source of truth.
2. Add narrow versioned API operations for conversations, task submission, status, cancellation and artifact references. Each request binds the user/device, Naut, authorized project and idempotency key. Reuse the existing service functions rather than rebuilding the agent loop in the phone.
3. Make disconnect/reconnect normal: persist run events with sequence numbers and explicit states such as queued/running/awaiting approval/failed/completed. Preserve launch receipts separately from test evidence. Do not require an SSE socket to stay alive for a job to continue.
4. Reuse inbox approvals and per-device revocation; add scoped mobile permissions and short-lived authentication. Keep diagnostic eval and unrestricted PTY control out of the ordinary Naut-app credential scope. Use an explicitly restricted tailnet connection for the first private version.
5. Route repository coding tasks through existing workers; finish validating/releasing the preview self-service tools before advertising them as production mobile behavior. Support non-repository personal tasks through bounded connector/tools, not by pretending every request is a Git task.
6. Add a separate browser-computer provider only if the product needs website interaction. Borrow the provider contract, per-Naut browser context, screenshot/action surface and approval cards from Open-Dots. Supply a real model observation/action loop and failure/credential/egress handling. Generic unattended desktop operation is another capability, not delivered by adding a mobile client.

Acceptance checks for this new work should exercise request retry without duplicate worker launch, phone disconnect/reconnect, app restart and unfinished-run reconciliation, stale/denied approval, revoked device token, wrong-project access, cancellation, and a completion claim with missing evidence. Existing backend test suites are useful foundations, not evidence these future mobile contracts already pass.

## Ideas worth borrowing

The strongest Open-Dots ideas for xNaut are its approachable persona/computer presentation, readable action previews, one visible action lifecycle, and a provider-neutral computer API. xNaut already has the more substantial coding and orchestration foundation. Building a clean mobile product on that foundation is the useful direction; adopting Open-Dots wholesale would also import a different model API contract, duplicate storage and permissions, and prototype defects.
