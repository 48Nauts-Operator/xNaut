## What the ticket asked, and what was found

The ticket's own next step was "reproduce with the console open, or drop the
timeout race so the real rejection surfaces", because it could not tell whether
`downloadAndInstall()` rejects or hangs.

That question was unanswerable **by construction**. `showUpdateBanner()` ran

```js
const timeout = new Promise((_, reject) => setTimeout(() => reject(new Error('Download timed out after 60s')), 60000));
await Promise.race([updateObj.downloadAndInstall(), timeout]);
```

When the timer won, the real `downloadAndInstall()` rejection **lost the race
and became a promise with no handler**. So the banner printed "Failed — download
manually" whether the request had 404ed, stalled on a socket, or simply not
finished yet. The code meant to report the failure was destroying the evidence,
which is why the cause survived every release.

Reading the plugin source (`tauri-plugin-updater` 2.9.0, in the cargo registry)
turned up three defects behind that race, each of which alone produces the
reported "sticks on Downloading...":

1. **No timeout ever reached Rust.** `downloadAndInstall()` was called with no
   options. `updater.rs:559` applies a reqwest timeout only `if let Some(timeout)
   = self.timeout`, so the client was built with **no timeout at all** — a
   stalled connect or hung TLS handshake hangs forever with no error. Not
   hypothetical here: `~/Library/Application Support/xnaut/debug.log` carries six
   `Update check skipped: error sending request for url (…latest.json)` lines
   from this machine. Same reqwest client, same host.
2. **No progress was subscribed.** The plugin emits `Started{contentLength}` /
   `Progress{chunkLength}` / `Finished` over a channel (`commands.rs`,
   `DownloadEvent`). Passing no `onEvent` left the UI unable to distinguish
   "never issued a request" from "downloading 26MB slowly" — exactly the question
   the ticket lists as STILL UNKNOWN, and one that can only be answered on the
   machine that has the problem.
3. **60s is shorter than the download.** `xNAUT-macos-aarch64.app.tar.gz` is
   26,509,010 bytes (measured, below). Any link under ~4Mbit reported failure on
   a download that was going fine.

And success was a dead end too: there is no restart anywhere in the plugin's
macOS install path, so the old comment `// Tauri will restart automatically` was
untrue. On a **successful** update the app was replaced on disk and the button
sat disabled on "Downloading..." forever.

## Change

`src/js/app.js` — the update flow no longer invents a verdict.

- `downloadUpdate()` replaces the `Promise.race`. It passes
  `{ timeout: 15 * 60 * 1000 }` so Rust builds a client that eventually errors
  instead of hanging, and passes an `onEvent` handler so the button shows real
  bytes (`Downloading 12.4 MB / 26.5 MB`).
- A watchdog **reports** a stall; it never cancels. If no bytes have arrived for
  `UPDATE_STALL_MS` (90s) it offers the manual download and logs
  `[updater] no progress for …ms after N bytes (started=…)` — but the real
  promise stays attached, so its eventual outcome is still reported. If bytes
  resume, the claim is taken back.
- Failures name the phase they died in — `request` (nothing ever answered),
  `download` (bytes started and stopped), `install` — and put the real error text
  on the banner as well as through `console.error`, which `debug-log.js` already
  forwards to `debug.log`. That is the diagnosis the ticket could not get.
- `updateInstalled()` handles the success case that previously did nothing.
- `checkForUpdates()`'s swallowed `console.log('Update check skipped:', e)` is now
  `console.warn('[updater] check failed:', e)`, so the field failures already in
  `debug.log` are greppable.

`src-tauri/Cargo.toml`, `src-tauri/src/main.rs`,
`src-tauri/capabilities/default.json` — added `tauri-plugin-process` 2.3.1 and
granted `process:allow-restart` (not `allow-exit`). This is what the banner's
"Restart now" calls; without it an installed update keeps running the old binary
with nothing in the UI to say so. `src-tauri/gen/schemas/*` are regenerated by
`tauri-build`.

`tests/update-banner.spec.mjs` — seven new tests driving a fake update object.

Not changed: the ACL for `updater:*` (the ticket ruled it out and this run
agrees — `updater:allow-download-and-install` is present and `check()` proves the
capability applies), the manifest, the endpoints, or the pubkey.

## What the tests prove

They drive a fake `window.__TAURI__.updater`, because the thing under test is the
frontend's contract with the plugin. The fake emits exactly the shapes fixed by
`commands.rs` (`#[serde(tag="event", content="data")]`, camelCase fields).

1. `downloadAndInstall()` is called with a numeric `timeout` > 60000 and a
   subscribed `onEvent`. Without both, Rust can hang with nothing to observe.
2. The button reports real bytes, not a fixed "Downloading...".
3. A download slower than the old 60s timer — progress every 150ms across many
   watchdog ticks, with the stall threshold shrunk to 400ms — is **not** called a
   failure. This is the regression test for the race itself.
4. A request that never answers is reported as `No response`, and the real
   rejection that follows still reaches the banner as
   `request failed: error sending request for url`.
5. An install failure says `install failed: …`, not `download failed`.
6. A resolved `downloadAndInstall()` offers "Restart now" and calls
   `process.relaunch()` — the successful-update dead end.
7. Without the process plugin the banner says "Quit and reopen to finish" rather
   than pretending it can restart.

The stall threshold is read through `updateStallMs()`, which honours
`window.xnautUpdateStallMs`. That is a deliberate test seam in the same spirit as
`tests/static-server.mjs`'s `__xnautStub`: a test cannot wait 90 seconds.

## How to verify it by hand

This needs a real signed release, which is why it is listed separately from the
suites above — nothing in this worktree can produce one, and `checkForUpdates()`
deliberately returns early when `resourceDir()` matches `worktrees` or
`target/release`, so a dev build never offers an update.

1. Install a release older than the current tag (e.g. the 1.13.9 bundle in
   `/Applications/xNAUT.app`) and launch it from `/Applications`.
2. Within ~3s of startup the banner should appear. Open DevTools
   (Cmd+Option+I) and click **Update Now**.
3. Expected now, and none of it was possible before:
   - the button counts real bytes, e.g. `Downloading 4.2 MB / 25.3 MB`;
   - on success it becomes **Restart now**, the banner reads
     `xNAUT vX.Y.Z is installed.`, and clicking relaunches into the new version
     (confirm with the version in the About menu);
   - on failure the banner names the phase and the real error, and the same line
     is in `~/Library/Application Support/xnaut/debug.log` prefixed `[updater]`
     — so the next report does not need DevTools at all.
4. To exercise the stall path without waiting: block the asset host
   (`sudo pfctl` or pull the network) after clicking. Within 90s the button must
   read `No response — download manually` or `Stalled — download manually` and
   become clickable, and the eventual reqwest error must still land on the banner
   rather than being swallowed.
5. Confirm the ACL is right by watching for `not allowed by ACL` in the console
   when Restart now is pressed. It must not appear; `process:allow-restart` is
   granted and `process:allow-exit` deliberately is not.

## Not finished

- **No end-to-end run against a real release.** Everything above is read from the
  plugin source, measured against the live asset over HTTP, and tested against a
  faithful fake. The one thing not done is clicking Update Now on a signed build
  and watching a real 26MB payload land, because that needs a release cut and
  installed outside this worktree. Step 3 of the manual section is exactly that
  check.
- **Which of the three defects actually fires in the field is still unproven.**
  The fix does not depend on knowing — a timeout, a progress subscription and an
  honest error report each close one of them, and whichever one it is now names
  itself in `debug.log` on the next attempt. That was the ticket's stated goal.
- **`agents::tests::configured_nautgate_route_preserves_claude_oauth_and_supplies_openai_token`
  fails on this box and is not mine to fix** — it requires a live NautGate on
  localhost:8090. Verified pre-existing on a clean tree. Worth its own ticket:
  either the test should start a stub endpoint or `endpoint_alive` should be
  injectable.
